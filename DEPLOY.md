# Local setup and optional future deployment

**Current scope is local only.** No Render, Neon, Cloudflare or GitHub project has been created or changed. The instructions below describe an optional later deployment; hosted behavior has not been verified.

## Local development

Install Python 3.12 and Node 22, then run from the repository root:

```sh
python3 scripts/dev.py
```

The helper creates the backend virtual environment if needed, installs missing dependencies, starts a native PostgreSQL server, applies Alembic migrations, and starts one API worker and Vite. Open http://localhost:5173. Data persists under `.local/postgres`; development secrets are stored in ignored `backend/.env` when it does not already exist. Ctrl+C stops the helper's services. An explicit DATABASE_URL environment variable uses an existing database instead of managed local Postgres. The first run needs internet access for dependencies.

To run services yourself, use `backend/.env.example` as a guide, generate distinct random secrets of at least 32 characters, apply migrations, and start one uvicorn worker. Never print or commit production secrets. API `/healthz` is a cheap liveness endpoint; `/readyz` also verifies secrets and PostgreSQL connectivity.

`docker compose up --build` is an alternative configuration, **not executed in this environment**. Its ports bind only to loopback, and its fallback secrets are public development-only constants. Set distinct JWT_SECRET, SALT_SECRET and CRON_SECRET values before any nonlocal use. The native helper is the verified local path.

## Optional: repository and Neon

1. Create a GitHub repository and push source, lockfiles, migrations and CI configuration. Exclude `.env`, `.local`, credentials and runtime data. Run the supplied CI workflow before deploying; it has not been run remotely here.
2. In Neon create a project using the intended free plan and a region near the API. Confirm current storage/compute allowances and region availability in the provider UI.
3. Open **Connect**, enable **Connection pooling**, and copy the pooled PostgreSQL connection string into the API's DATABASE_URL secret. Keep TLS enabled. Pulse normalizes the asyncpg dialect, translates sslmode to ssl, and removes the libpq-only channel_binding parameter. See [Neon's pooling documentation](https://neon.com/docs/connect/connection-pooling).

## Optional: Render API

1. Choose **New → Blueprint**, connect the repository, and review `render.yaml` before applying it.
2. Keep exactly one Python web service, the intended free plan and an available nearby region. The supplied blueprint uses Singapore. Review the current [Blueprint reference](https://render.com/docs/blueprint-spec) if the dashboard rejects a setting.
3. Set DATABASE_URL to Neon, ALLOWED_ORIGINS to the exact final dashboard origin, and PUBLIC_API_URL to the final HTTPS API origin. JWT_SECRET, SALT_SECRET and CRON_SECRET are generated by the blueprint. Keep these stable across restarts. Leave LLM_API_KEY unset; the profiler uses rules.
4. The build installs the runtime lock. Startup applies migrations and launches exactly one worker:

   ```sh
   alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT --workers 1 --no-access-log
   ```

5. Check `/healthz`, `/readyz` and `/docs`. Create an account, add a public monitor and verify that actual timed checks arrive. Never expose the database port or place secrets in VITE_ variables.

Render currently documents idle spin-down after 15 minutes and a shared monthly free-hour allowance. Review [free-service limits](https://render.com/docs/free) before relying on always-on monitoring. Pulse reports observation gaps; no free-host uptime or capacity guarantee is made.

## Optional: Cloudflare Pages

1. Open **Workers & Pages**, create a Pages project and connect the repository.
2. Set root directory `web`, build command `npm run build`, output `dist`, Node version 22 and VITE_API_URL to the API's HTTPS origin. The repository checkout must include sibling `tracker`, because the web build also builds the API tracker asset.
3. Deploy and copy the Pages origin into Render's ALLOWED_ORIGINS. Keep only intended origins in the allowlist.
4. Verify `/`, `/welcome`, `/dashboard`, a nested monitor route after hard reload, login, the tracker install flow, an opted-in status page, and the controlled demo. `web/public/_redirects` supplies SPA routing. The static landing page works without waking the API.

See [Cloudflare's build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/). If a provider builds only the selected root rather than the full checkout, build the tracker in CI first and deploy the web output separately.

## Optional: external cron

1. Create a cron-job.org job pointing at `https://<API>/api/cron/tick`.
2. Use POST every five minutes, with custom header **X-Cron-Secret** equal to the API's CRON_SECRET. Do not put the secret in the URL.
3. Run the job manually and verify a successful response and new monitoring activity. Enable failure notifications if desired. Check both providers' current usage rules before enabling recurring requests.

The tick is implemented and secret-protected. It triggers overdue probes, retention and rollups in the existing process, with a lock to prevent overlapping ticks. It does not create another worker. Startup heartbeat gaps and missing probe coverage remain visible after downtime.

## Alert setup

In a live monitor's Settings, add a generic, Slack, Discord or Telegram channel. All destinations require HTTPS and the same pinned-IP SSRF guard as probes. Redirects are refused. For Telegram use `https://api.telegram.org/bot<TOKEN>/sendMessage` and a separate chat ID; see the [Bot API contract](https://core.telegram.org/bots/api#sendmessage). Destination secrets are stored in the local database and omitted from API responses. Real provider delivery requires your credentials and has not been exercised here; automated tests substitute the outbound transport.
